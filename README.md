# AIOS 交通平台：AI 辅助可行性实验

**状态：2026-11-08 第五轮，运行接入与已知任务回归，不是已完成的参赛作品。**

本仓库由 AI 助手在用户授权下建立，包含生成/辅助编写的可行性脚本、有限兼容修正和验证工作流。不能将其直接署名为学生独立完成的竞赛核心实现；正式参赛需要学生实质参与、理解验证结果并如实披露 AI 使用。

## 已实际完成

- 下载并校验官方 `Qwen/Qwen3-8B-GGUF` 的 Q4_K_M 权重，在 GitHub 托管 Linux **CPU** 运行器内本地推理。没有调用商业云端大模型 API，也不是在用户 RTX 4090 上运行。
- 首批四个独立模型审查上下文及汇总实际执行，保留错误意见；它们没有自主工具或网页访问，不能冒充四类业务智能体。
- 通过固定版本的 Cerebrum 开发工具包、AIOS 原始调度器/模型管理器/工具管理器，执行真实 CityFlow 交通回归。
- 单个 8B 智能体实际完成五步：读取任务 → 计算九个候选 → 执行所选方案 → 读取实际验收 → 结束。
- 选中 `r1-task`：通行时间505个模拟秒，平均排队相对基准增加4.938081%，满足事先给定的5%上限。更快的478秒方案超过上限，没有被选中。
- 选中方案在全新仿真进程重跑；原始路线、目的地、相位和业务指标经过离线检查。`r1-task` 与 `r1-bounded` 是数值目标上的并列最优。
- 原生 AIOS 内另运行四个带规则事实的审查上下文。未进行正式的四专业交通团队实验。

## 调用链与修改范围

模型意图经原生 SDK 发送至 AIOS，AIOS 使用已有的 OpenAI-compatible 客户端分支调用本机 llama.cpp。配置中的 `vllm` 是适配器分支名称，**不表示本次运行了 vLLM 服务**。

AIOS 原件保留，兼容副本仅修正入口中 `ToolQuery` 的字段以及漏传的温度、输出长度、响应格式。调度器与管理器没有替换。SDK显式源码路径只写入临时运行器。CityFlow只加入只读信号相位接口，不改车辆动力学。

内存与存储只初始化，未作功能验收；Redis连接不可用。未使用的桌面MCP服务明确关闭，不声称桌面或MCP执行通过。

## 已知评价问题

`verify_execution` 中的 `best_within_exhaustive_candidate_set` 原始字段比较候选名称与规范排序赢家；因此会把数值上同样最优的 `r1-task` 标为false。原始轨迹不改写。独立离线检查按合同规定的 `(通行时间,平均排队)` 判断，确认它与 `r1-bounded` 数值并列最优。这是本试验包装代码的评价语义问题，不是模型选错。

首批模型审查错误地把共享权重等同于同一种智能体，还算错工具节时比例；后续显式提供证据。审查文本不是事实裁判，第二批也未做提示策略的受控效果实验。

## 不能声称的成果

- 静态任务只有9个候选且预算也是9，强脚本能够穷举；不是多智能体必要性证据。
- 四个计算进程、四个独立审查上下文，都不等于满足了四类业务智能体和三对双向协作。
- 135.36秒是服务就绪后的一次CPU单智能体回归墙钟时间，不包括安装和服务启动，也不是串并行比较。
- 没有证明端到端减少20%，没有测得多智能体优于强单体或强脚本。
- 没有真实道路控制、应急车辆行为或道路安全认证。

## 复现

在 Actions 手动运行 `Native AIOS traffic regression`，或修改其专属工作流文件触发一次运行。工作流有50分钟上限、内容只读权限、固定公开依赖与独立日志；没有定时任务。运行可能因上游下载或依赖服务失败，失败产物也会保存。

下一阶段应验证动态事件、跨专业证据反馈与公平单体基线，而不是继续扩充已被穷举解决的静态候选题。
