# B1 只读多轮接入准备

本目录提供一个可审查、可重新生成的最小接入补丁。它复用冻结 G1 的真实 Cerebrum SDK（开发工具包）→ AIOS（智能体操作系统）调度器 → 固定本地 Qwen3-8B 模型 → 原生只读工具调用链，增加三轮模型请求、两次实际工具结果反馈、逐请求原始正文留存和预算计量。

**本次关闭 Web 界面的新候选仅作本地生成和有限验证，尚未发布或运行，没有取得真实模型资格，也没有得到 B1 恢复成绩。** 上一候选的真实运行 `44493647753` 在模型服务镜像构建阶段失败；该结果不能算作模型接入验证。本目录没有修改 `g1-smoke` 或 `b0-run`。

## 1. 从实际源码定位的缺口

| 冻结文件 | 实际行为 | 本补丁的最小改动 |
| --- | --- | --- |
| `g1-smoke/payload/integration/g1_sdk_client.py` | 发一次 `LLMQuery`（模型查询），让模型从两个公开读取中选一个；随后仅调用工具，结果没有再次进入模型 | 仍使用实际 SDK，改为读取选择 → 实际读取反馈与第二项选择 → 实际读取反馈与结束，共三次模型请求 |
| `g1-smoke/payload/integration/agent_entry.py` | 模型服务使用 2048 上下文、一个并发槽；模型日志和 AIOS 调用计数必须恰好为一次 | 派生包明确使用 4096 上下文，计数必须恰好三次，并在所有自有进程关闭后重新核对原始正文及预算记录 |
| `g1-smoke/payload/sdk/cerebrum/utils/communication.py` | SDK 直接发 HTTP 请求，无显式超时和逐请求原文记录 | 保留 `send_request` 原接口及报文结构，在它原来的 `post` 位置加入限定目的地、显式超时、零自动重试和实际 HTTP 正文记录 |
| `g1-smoke/payload/sdk/cerebrum/llm/apis.py` | 查询没有请求标识，响应没有原始用量字段 | 增加可选 `request_id`（请求标识）、`usage`（供应端原始用量）、`model_metadata`（模型响应关联信息） |
| `g1-smoke/payload/integration/source_terminal/runtime/launch.py` | 内核接收请求后重新构造 `LLMQuery` | 重新构造时保留请求标识，避免计量记录与真正执行的查询失去关联 |
| `g1-smoke/payload/integration/source_terminal/aios/llm_core/adapter.py` | 已有真实 OpenAI 兼容客户端；取得响应后只返回正文或工具调用，丢弃 `usage` 等字段；没有显式禁用 SDK 自动重试 | 使用同类客户端及原 `_get_model_response` 路径，设定 `max_retries=0`，通过 HTTPX 请求/响应钩子留存实际正文，再把原始用量和正文摘要写回真实 `LLMResponse` |

模型仍是固定的 `Qwen3-8B-Q4_K_M.gguf`，权重 SHA-256（文件摘要）为 `d98cdcbd03e17ce47681435b5150e34c1417f50b5c0019dd560e4882c5745785`，原模型服务、Python 依赖、Cerebrum SDK、AIOS 调度及原生工具进程继续来自冻结包。本补丁没有重写一个替代的模型回答器。

## 2. 三轮行为的准确边界

第一轮模型在 `backup_catalog`（备份目录）和 `receipt_bundle`（业务回执包）中选择一项。驱动把选择转换成原有 `ToolQuery`（工具查询），经原 `SafeToolManager`（受限工具管理器）和原生隔离进程逐片接收公开文档。沿用原 `PublicDocumentAssembler`（公开文档拼装器），校验运行标识、世界版本、程序摘要、片段顺序和完整文档摘要。

第二轮模型收到第一份文档的真实摘要、字节数、行数、覆盖范围与一致性标记，必须复述实际摘要与行数，再选择尚未读取的另一项。完成第二次原生读取后，第三轮模型收到对应结果，必须返回同样的绑定字段，并以 `read_only_no_recovery_verified`（只读完成，尚未验证恢复）结束。

模型收到的是**明确声明的行数与覆盖范围投影**。完整公开文档保存在证据中，未全部加入模型上下文。继承的 `complete_public_snapshot` 字段仅表示所选两份文档通过完整传输校验；`global_state_complete` 始终为 `false`，不表示取得全局系统快照。

摘要和行数复述只证明后续模型回合绑定了刚收到的实际反馈，不证明模型理解了业务内容、作出了正确诊断或具备恢复能力。第二项读取被限制为尚未读取的选项，整个流程不能充当“最强单智能体 B1”。后续 B1 求解器仍须获得与多智能体等价的公开信息、合法工具、完整 B0 辅助程序及公平预算，另行预注册和评估。

## 3. 预算和失败语义

| 约束 | 固定值或规则 |
| --- | --- |
| 模型请求 | 最多三次，必须恰好三次才能通过本接入门禁 |
| 单次输出 | 最多 192 个词元，直接传给实际模型请求的 `max_tokens` |
| 总输出预留 | 576 个词元；预留量不是实际消耗量 |
| 输入 | 每次序列化查询最多 16000 字节；不把字节数冒充输入词元数 |
| 上下文 | 4096 个词元、一个模型槽；与冻结 G1 的 2048 配置不同，不能直接比较时延 |
| SDK 调用 | 最多 1027 次，即三次模型请求与两份文档各最多 512 片工具调用 |
| 客户端 | 整体 900 秒；实际模型 HTTP 请求超时 180 秒；保留原外层进程清理期限 |
| 工作流基础设施上限 | 96 分钟，容纳运行、清理、封存与上传；模型、客户端及智能体期限不因此增加 |
| 重试 | SDK 和模型客户端均为零自动重试；拒绝同一标识再次分派 |
| 资源 | 沿用四个 CPU、8 GiB 内存、无 GPU；越界失败，不自动增加资源 |

每次模型请求先在 SQLite 数据库中提交预算预留，再通过 SDK 发出。真正到达 AIOS 适配器时，查询内容必须与预留内容一致；记录状态转为执行中，才允许原模型客户端调用。任何断连或不明结果都保留原请求槽与输出预留，状态记为 `unknown`（未知），不继续发起下一轮模型请求。若已经取得并保存完整后端响应，之后发生客户端断连，也不会删除已知的用量与正文。

供应端 `usage` 原对象完整保留，不估算、不填零。缺字段、非法计数或没有返回响应，均保留未知值。汇总同时提供已知部分之和、未知请求数和只有所有请求均提供该字段时才存在的完整合计；还单独报告供应端总数不一致、输出词元超过预留等问题。

接入门禁允许供应端用量缺失，以便诚实记录接口能力；这时 `usage_complete=false`，不得宣称已具备精确词元成本比较。输出量已知且超过预留则门禁失败。后续成本对照需要把用量完整性另设为评估条件。

## 4. 原始证据与独立复核

每次实际 SDK 与模型调用分别保存到：

```text
<运行日志>/b1-metering/requests.sqlite
<运行日志>/b1-metering/sdk/<请求标识>/request.json
<运行日志>/b1-metering/sdk/<请求标识>/response.json
<运行日志>/b1-metering/model/<请求标识>/request.json
<运行日志>/b1-metering/model/<请求标识>/response.json
```

这些是实际 HTTP 应用层请求/响应正文，使用独占创建和文件同步写入；不声称是包含所有报头和网络帧的完整抓包。原响应中的供应端响应标识、模型名、结束原因和原用量保留在原文及关联记录里。断连时响应文件可以缺失，该缺失必须进入证据摘要并阻止门禁通过。

SDK 另保存两份完整公开文档、实际反馈投影以及各轮结构化查询。父进程结束自有模型和内核进程后，再从数据库读取状态，重新计算全部 SDK 与模型正文文件摘要，并结合原模型服务日志、原 AIOS 函数观测和宿主无提交检查判定结果。日志目录中的本地账本不是独立安全认证；宿主原有边界证明和原生调用日志继续保留。

只允许本地模型地址 `http://127.0.0.1:19080/v1`、本地内核地址 `http://127.0.0.1:19082` 和固定模型别名。客户端不读取代理配置，不接受任意云端模型地址；保留原内核网络审计、只读工具白名单、原生调用隔离与零提交约束。

## 5. 文件与生成方式

| 文件 | 用途 |
| --- | --- |
| `build_overlay.py` | 校验冻结 G1 的全部 262 个文件，在新的目录生成派生副本，按唯一源码锚点施加补丁，生成原文件前后摘要与新包清单 |

| `LOCAL_VALIDATION.json` | 本次本地验证记录，明确标注未执行的远程条件 |
| `UI_BUILD_SOURCE_BINDING.json` | 固定 llama.cpp 构建来源、上一场真实错误证据和关闭 Web 界面的适用前提 |

冻结 G1 包清单摘要为 `948a410a3ecc63954ad505df14dd0c9845742119c7f98a96da808d273a7bbfce`。任何基包文件、文件集合或清单变化都会拒绝生成。所有改动只写入新目标目录，禁止覆盖现有目标，也拒绝把目标放入冻结基包内部。

本地生成示例：

```bash
python -B b1-readonly-gate/build_overlay.py \
  --dest /workspace/scratch/a11dd1f2a296/b1-local-review-new \
  --branch sre-b1-readonly-ui-off-20261119
```

`--branch` 仅把未来专用分支写入生成包的已有宿主运行入口；生成器不创建或推送分支，不生成工作流，不调用远程服务。审查新包的 `OVERLAY_MANIFEST.json` 与 `execution_plan.json` 后，主线再按现有授权安排后续行动。

分支绑定同时覆盖总运行入口、原生宿主入口、资源所有权领取及证据导出的正式运行路径。`native_host_runtime.REF` 仍由总运行入口的 `configure` 动态覆盖，不另行改动；其他宿主条件、既有独立导出诊断分支和资源名称前缀保留。最终封存结果明确标注为未评分的 B1 只读多轮工程资格，不沿用原 G1 正式结果标签。测试直接调用实际入口的分支检查，验证新分支接受、旧 G1 正式分支拒绝；原生入口在通过检查后的第一次输出目录创建前主动停止，资源枚举使用明确夹具，因此没有部署、清理或导出真实基础设施。


## 6. 固定版本 Web 界面构建修正

上一候选保留了冻结 G1 的原 Dockerfile（镜像构建配方）。真实运行日志显示固定的 llama.cpp 提交 `f7591a6a01f9273de03331732bdc0b39721168be` 已完成源码抓取、配置并进入编译，随后在提供 Web 界面资源时失败。其命令中 `HF_ENABLED=ON`、`BUILD_UI=OFF`；请求版本 `b1` 的校验文件发生 HTTP 错误后，下载器回退到 `latest`（浮动最新版本），成功校验并解压该资源，但固定脚本要求的 `workbox[hash].js` 缺失，因此停止构建。这属于原构建路径与外部界面资源不相容，不能仅解释为临时下载失败；模型、SDK 和新增 Python 逻辑当时尚未得到运行验证。

本次生成器只在派生 Dockerfile 的原 CMake 命令中增加 `-DLLAMA_USE_PREBUILT_UI=OFF -DLLAMA_BUILD_UI=OFF`，使用该固定提交已经提供的两个官方选项。固定源码的[顶层 CMake 配置](https://github.com/ggml-org/llama.cpp/blob/f7591a6a01f9273de03331732bdc0b39721168be/CMakeLists.txt)定义选项，[界面目标](https://github.com/ggml-org/llama.cpp/blob/f7591a6a01f9273de03331732bdc0b39721168be/tools/ui/CMakeLists.txt)将其传给[资源生成脚本](https://github.com/ggml-org/llama.cpp/blob/f7591a6a01f9273de03331732bdc0b39721168be/scripts/ui-assets.cmake)。两项关闭时，脚本跳过 npm（前端包管理器）构建与 Hugging Face 界面资源下载；在没有已有 `dist/index.html` 的情况下，仍由原 `emit_files` 函数生成零资源表及对应头文件，保留服务端构建目标。

该行为有明确前提：脚本仍会优先使用源码目录中预先存在的界面资源，也会检查已有构建目录中的资源。当前 Dockerfile 在新的 `/tmp/llama` 目录检出固定提交，官方目录清单不含预构建 `tools/ui/dist`；没有把旧失败镜像层中的下载文件复制进来。本修正没有放宽资源校验、加入临时重试、修改模型权重或源码提交，也没有改变模型、SDK、词元预算、上下文和期限。

现有十四项本地夹具验证继续使用原调用链及预算逻辑，宿主分支检查绑定新候选 `sre-b1-readonly-ui-off-20261119`。本地环境没有 Docker 和 CMake，因此没有执行这条 CMake 分支、编译服务端或验证最终镜像。固定源码阅读、派生文件差异与夹具结果仅支持这项最小候选修正；真实构建和模型资格仍待新的远程结果。
